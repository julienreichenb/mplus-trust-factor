M+ TRUST FACTOR — PROCESS FLOWS
==============================

1. Character search and refresh
-------------------------------
User enters region + realm + character.

API:
1. Normalize identity.
2. Look up Character.
3. If a fresh score snapshot exists, return it immediately.
4. If data is stale but usable, return stale data with `refresh_status=QUEUED` and enqueue refresh.
5. If no data exists, create/resolve Character and enqueue a high-priority refresh.
6. Return 202 with job status when synchronous completion is not feasible.
7. Apply per-character manual refresh cooldown.

Worker refresh DAG:
A. Blizzard identity/profile/equipment/spec/talents/current M+ profile.
B. Minimal Raider.IO profile fields and current/previous season context.
C. Warcraft Logs public character/rankings/report discovery.
D. Normalize and upsert.
E. Identify latest and highest detailed runs.
F. Fetch missing detailed reports/events only.
G. Extract metric observations.
H. Compute authenticity, dimension scores, confidence, overall score, and grade.
I. Persist immutable ScoreSnapshot.
J. Invalidate API response cache.

2. Scheduled refresh
--------------------
- Refresh active/eligible characters by priority.
- Priority factors:
  - Recently searched.
  - Recently active.
  - Near top-25% threshold.
  - Previously exported to addon.
  - Score data older than TTL.
- Do not refresh every stored character at the same frequency.
- Use a provider budget controller.
- Old/inactive characters progressively move to longer refresh intervals.

3. External request policy
--------------------------
Before any request:
- Build canonical request fingerprint.
- Check PostgreSQL/Redis cache.
- Check negative cache.
- Check provider circuit breaker.
- Acquire provider token-bucket slot.
- Check job cancellation/staleness.

After response:
- Record status, timing, headers, cost, and provider.
- Honor Retry-After.
- Retry only idempotent requests.
- Use exponential backoff with jitter.
- Persist payload hash and provenance.
- Redact credentials.
- Update cache TTL.
- Release queue slot.

4. Warcraft Logs detailed analysis
----------------------------------
For each selected run:
1. Resolve report code and fight ID.
2. Fetch report revision and fight metadata.
3. If same revision is already analyzed with current analysis version, skip.
4. Fetch master data once with `translate: false`.
5. Resolve target actor/source ID.
6. Fetch only required event/table categories:
   - Casts
   - Interrupts
   - Deaths
   - DamageTaken
   - Buffs/Debuffs where needed
   - Dispels
   - Healing only where needed for external support
   - CombatantInfo if gear/loadout is required
7. Restrict to selected fight ID and target source/target where possible.
8. Follow `nextPageTimestamp` pagination.
9. Store compact normalized observations; large raw pages go to compressed artifacts.
10. Compute coverage and limitations.
11. Do not fetch every event type by default.

5. Metric computation
---------------------
- Provider adapters produce normalized facts.
- Metric extractors turn facts into MetricObservations.
- Normalizers transform raw values to 0–100 using model/config context.
- A metric observation includes:
  - raw value
  - normalized value
  - confidence
  - source
  - context
  - time window
- Missing metrics remain missing; do not fabricate zero.
- Dimension confidence reflects coverage and data quality.
- Low-confidence dimension scores are shrunk toward 50.
- Overall score is calculated from a versioned model.
- Save explanation contributors and input fingerprint.

6. Boost/authenticity computation
---------------------------------
1. Build current-season progression timeline.
2. Calculate key-level jumps and time gaps.
3. Inspect roster overlap in top runs.
4. Compare teammate ratings to target rating at run time when available.
5. Compare target's detailed performance in top runs.
6. Compare run volume and breadth to regional peers.
7. Detect confirmed/probable reroll context.
8. Add suspicion signals and mitigations.
9. Produce:
   - authenticity score
   - evidence list
   - red flags
   - confidence
10. Do not make a categorical accusation.

7. Comparison page
------------------
- Input 2–10 character identifiers.
- Resolve latest score snapshot for the same active model and season.
- Return:
  - global score and grade
  - dimensions
  - confidence
  - red flags
  - deltas from group median and best candidate
- Frontend renders overlaid radar charts and sortable comparison table.
- Do not silently compare scores from different model versions.

8. Admin model lifecycle
------------------------
1. Admin creates draft model from active model.
2. Admin changes weights, thresholds, normalization parameters, or red-flag rules.
3. Validate:
   - dimension weights sum to 1.
   - nested metric weights are valid.
   - thresholds are ordered.
   - formulas are supported.
4. Run backtest on fixture cohort.
5. Show distribution and major changes.
6. Activate new immutable version.
7. Queue recalculation.
8. Keep old snapshots queryable.

9. Addon export
---------------
Scheduled daily:
1. Select active model and current season.
2. Select eligible EU characters.
3. Keep only addon-safe summary:
   - canonical identity
   - overall integer score
   - grade
   - confidence bucket
   - limited public red-flag bitset
   - freshness date
4. Partition into deterministic Lua shards.
5. Generate metadata, checksum, format version, and character count.
6. Run Lua syntax and lookup tests.
7. Build addon artifact.
8. Record AddonExport.
9. CI may publish a release/package later.

10. Production deployment
-------------------------
CI:
- install with frozen lockfile
- lint
- typecheck
- unit/integration tests
- build
- vulnerability checks
- build and scan images
- push immutable image tags to GHCR

CD:
- SSH to Ubuntu VPS
- pull compose definition and images
- create database backup
- run migration job
- start services
- wait for health checks
- smoke test
- retain previous image tag for rollback
- roll back on failed health check
