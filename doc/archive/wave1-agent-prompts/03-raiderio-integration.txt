AGENT 3 — RAIDER.IO MINIMAL PROVIDER
===================================

Start in Cursor Plan mode.

Role and ownership
------------------
Implement a deliberately minimal, replaceable Raider.IO provider.

Primary ownership:
- `packages/providers/raiderio/**`
- `doc/api/raiderio/**`
- fixtures under `tools/fixtures/raiderio/**`

Official sources
----------------
- https://raider.io/api
- https://raider.io/swagger.json
- https://raider.io/settings/apps
- https://raider.io/mythic-plus/cutoffs
- https://support.raider.io/kb/frequently-asked-questions/how-does-the-mythic-plus-leaderboard-slash-api-capacity-work

Plan-mode deliverable
---------------------
Write `doc/plans/03-raiderio.md` before code. Include:
- Exact current OpenAPI parameters and response fields.
- Minimal call matrix.
- Terms/attribution summary.
- Replaceability plan.
- Rate limiter and TTL.
- Data required for boost features.
- Fields explicitly excluded.
- No implementation until review/transition.

Business constraint
-------------------
Raider.IO is useful but potentially sensitive for a competing/commercial service.
The public docs currently:
- state 200 unauthenticated requests/minute;
- require attribution for public-facing use;
- prohibit competing services/resale without permission;
- direct commercial users to contact Raider.IO.

Therefore:
- Use the strict minimum.
- Never scrape.
- Keep all Raider.IO code behind the shared provider interface.
- Record every field dependency.
- The system must remain functional, with reduced richness, if Raider.IO is disabled.

Allowed MVP operations
----------------------
After live OpenAPI verification:
1. `GET /api/v1/characters/profile`
   - only for a newly searched or stale character
   - exact minimal fields
2. `GET /api/v1/mythic-plus/season-cutoffs`
   - EU
   - daily cache
3. `GET /api/v1/mythic-plus/static-data`
   - season/dungeon mapping
   - long cache
4. `GET /api/v1/mythic-plus/run-details`
   - only for a selected latest/highest run when necessary
   - skip if profile/other provider already supplies required roster
5. `GET /api/v1/periods` only when needed for season/week context

Do not use `/api/v1/mythic-plus/runs` for broad crawling in the MVP.
Do not use live-tracking endpoints.

Character fields to verify
--------------------------
Request only fields actually needed, potentially:
- mythic_plus_scores
- mythic_plus_scores_by_season
- mythic_plus_recent_runs
- mythic_plus_best_runs
- mythic_plus_highest_level_runs
- mythic_plus_ranks
- raid_progression
- gear only as fallback, not duplicate Blizzard by default

The current field syntax may include season selectors. Verify it live and document exact examples.

Normalized outputs
------------------
- Current and previous season score summaries.
- Recent run candidates.
- Best/highest run candidates.
- Roster/teammate identities.
- Character regional rank/percentile context where returned.
- Raid progression summary.
- Regional cutoff values, especially top 25%.
- Static dungeon/season mapping.
- Source attribution URLs.
- Freshness.

Do not return provider DTOs directly to the public API.

Boost-support facts
-------------------
Expose neutral facts for Agent 4:
- Run timestamp.
- Dungeon/key/duration/timed.
- Target character score/rank at current snapshot.
- Teammate identities.
- Teammate current score/rank if present in the same documented payload.
- Roster recurrence across runs.
- Current/previous season history.
- Run volume represented by API data.
- Explicitly mark incomplete run history.

Do not compute "boosted".

Efficiency policy
-----------------
- Token bucket soft limit: 60 requests/minute.
- Concurrency: 2.
- Configurable.
- Honor 429 and Retry-After.
- Exponential backoff with jitter.
- Character TTL: 12 hours.
- Negative cache: 30–60 minutes.
- Cutoffs: 24 hours.
- Static data: 24 hours to 7 days.
- Request fingerprint and in-flight dedupe.
- One profile request should contain the exact minimal field set.
- No profile refresh on every page load.
- Manual refresh is subject to global character cooldown.
- Collect provider request counts and cache-hit metrics.

Attribution
-----------
Provide a normalized attribution object and document where the frontend must display:
- "Data from Raider.IO"
- link to relevant profile/source when its data is used

Acceptance criteria
-------------------
- No HTML scraping.
- No broad `/runs` ingestion.
- One stale character refresh uses the minimum documented number of calls.
- Provider can be disabled by configuration.
- Cutoffs are cached and expose top-25% threshold.
- Normalized run/roster data supports later authenticity analysis.
- Rate limiter remains under configured soft RPM.
- Public DTO includes attribution when Raider.IO-derived values are shown.
- Lint, typecheck, tests, build pass.
- `doc/agents/03-raiderio.md` is complete.

Do not
------
- Implement commercial usage assumptions.
- Add live-tracking calls.
- Duplicate Blizzard equipment calls by default.
- Make score computation dependent on Raider.IO availability.
