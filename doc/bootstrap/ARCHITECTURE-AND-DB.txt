M+ TRUST FACTOR — TARGET ARCHITECTURE AND DATABASE CONTRACT
===========================================================

1. Technology baseline
----------------------
Use current stable releases at implementation time and pin exact versions in lockfiles/container images.

Required stack:
- Monorepo: pnpm workspaces.
- Language: TypeScript with strict mode.
- Web: Vue 3, Vite, Vue Router, Pinia.
- UI: a lightweight component approach; avoid locking core domain logic to a UI library.
- Charts: Apache ECharts radar chart or an equivalent mature library.
- API: Node.js active LTS + Fastify.
- API contracts: OpenAPI generated from route schemas.
- Validation: Zod or Fastify-compatible JSON schema with inferred TypeScript types.
- Database: PostgreSQL.
- ORM/migrations: Prisma.
- Queue/cache: Redis + BullMQ.
- Tests: Vitest, Supertest/Fastify inject, Playwright, Testcontainers where useful.
- Logs: Pino structured JSON.
- Containers: Docker and Docker Compose.
- Production reverse proxy: Caddy unless Agent 8 documents a stronger reason for another choice.
- Package images: GitHub Container Registry.

3. Architectural rules
----------------------
- Provider packages return normalized domain DTOs and retain raw provenance.
- Provider packages do not compute the final Trust Factor.
- Scoring package is deterministic and performs no network calls.
- API routes do not call providers synchronously without a timeout and refresh policy.
- Long ingestion and analysis work runs through BullMQ.
- Website reads stable API DTOs, not provider-specific payloads.
- Addon exporter reads score snapshots, never external APIs directly.
- External requests are deduplicated, cached, rate-limited, and observable.
- A raw provider response must be linked to normalized records through provenance metadata.
- No agent may silently change shared contracts after Agent 0. Proposed changes go into
  `doc/contracts/change-requests/<agent>-<topic>.md` unless explicitly coordinated.

6. Canonical character and run matching
---------------------------------------
Character key:
- Prefer stable provider canonical IDs when available.
- Otherwise use normalized `(region, realm_slug, character_name)`.
- Keep aliases for renames/transfers.
- Normalize Unicode using NFKC and a stable lower-case strategy, but preserve display names.

Run canonical fingerprint proposal:
SHA-256 of:
- region
- season canonical key
- dungeon canonical key
- completed_at in milliseconds if available
- key level
- duration
- sorted roster canonical keys

If one provider has lower timestamp precision, perform candidate matching with bounded tolerances and
store the match confidence. Never merge runs only because dungeon, level, and date are similar.

7. Database acceptance expectations
-----------------------------------
- Initial migration applies on an empty PostgreSQL database.
- Seed creates EU region, a placeholder current season, model v1, metric definitions, grade thresholds,
  and red-flag definitions without fake production scores.
- Unique constraints make ingestion idempotent.
- Useful query indexes exist.
- Timestamps are UTC.
- Numeric score fields use sufficient precision and are clamped at service boundaries.
- Large event payloads are not blindly stored uncompressed in PostgreSQL.
